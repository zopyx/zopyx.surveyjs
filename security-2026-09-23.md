# Security review — zopyx.surveyjs

Date: 2026-09-23
Reviewed commit: `873ff30b1dfa6d254434c7a0143154bf8e7e6707` (`master`)
Scope: Plone access control, submission validation and storage, direct embedding, exports/rendering, outbound integrations, dependencies, container and CI configuration.

This was a read-only review. No project source files were changed. The working tree was clean after verification.

## Executive summary

The review found deployment-critical risks in the default Docker path, a direct-embed authorization bypass, stored click-triggered XSS in submission details, spreadsheet formula injection, and missing submission-rate enforcement. Existing controls include Plone POST authentication, bounded payloads, server-side validation, origin checks, and private-address checks for outbound POST endpoints, but these do not close the findings below.

## Findings

### Critical if deployed with repository defaults — fixed privileged credentials

`buildout.cfg:4-10` extends `test_plone60.cfg`, which includes `base.cfg`; `base.cfg:29-32` configures a fixed instance administrator credential. `Dockerfile:44-50` builds and starts that configuration. The init script also seeds a fixed Editor account (`scripts/init_plone.py:2322-2332`). The Docker workflow publishes the image and deploys it to the public host on pushes to `master` (`.github/workflows/docker-image.yml:4-8,104-126`).

If the deployed image retains the defaults, a remote user who knows the committed credentials can administer Plone and read or modify surveys and results. The actual public instance was not tested, so this finding is conditional on the deployed credentials not being overridden.

Remediation: remove fixed credentials from the production build path; provision unique credentials at deployment; disable demo-account seeding outside isolated demo environments; rotate any defaults used by an existing deployment.

### High, conditional on the CI AI secret being configured — AI key persisted in the image

The workflow supplies AI settings as BuildKit secrets, but `scripts/init_plone.py:140-163` writes the API key into the Plone registry. That function is called at line 702 and the site transaction is committed at line 2332. `Dockerfile:45-48` runs initialization during the image build and does not remove the resulting site database. With the default local ZODB configuration, the registry value is therefore persisted in the image’s database layer; anyone able to pull the image may be able to extract it.

The control-panel bootstrap also includes the raw API key in page JSON (`browser/controlpanel.py:112-121`, `browser/forms_settings.pt:37-40`), accessible to users with the settings-page permission.

Remediation: rotate keys included in existing images. Create the site without secrets during image construction and inject them at runtime from a secret manager; return masked/empty secret values to the browser rather than serializing the stored value.

### High — direct-embed token is not bound to the survey receiving a submission

In `browser/views.py:697-781`, `save_poll` validates the target survey’s allowlisted Origin and validates the JWT, but does not compare its `sub` claim with the target survey UID. It then skips trusted-access and survey-auth-token checks. The configuration endpoint does check the subject (`browser/embed_direct.py:194-202`), so this protection exists on one path but is missing from submission.

Preconditions: direct embedding is globally enabled; the target survey allows the token’s origin; and the caller has a valid token for another survey bound to that origin. A token issued for survey A can then be accepted by survey B’s save endpoint, potentially bypassing B’s trusted-access restriction and writing an unauthorized submission. The Plone authenticator remains required, but the anonymous authenticator is site-wide rather than survey-bound; the embed configuration returns it and the client submits it (`browser/embed_direct.py:213-237`, `browser/static/embed-client.js:104-117`). One-use JTI tracking limits reuse of the token but does not bind it to the intended survey.

Remediation: require `payload["sub"]` to match the target survey UID and check the target’s embedding mode before enabling the direct-embed path. Add a save-poll regression test for a token from A submitted to B.

### Medium — stored, click-triggered XSS in submission details

The validator rejects selected markup and strings beginning with `javascript:`, but does not parse URL attributes in otherwise allowed markup (`data_validation/data_validation.py:37-41,218-238`). A public submission containing `<a href="javascript:alert(document.domain)">review</a>` passes validation. A local probe confirmed the actual `SurveyConverter` → Markdown → HTML path preserves this anchor.

The detail view builds HTML from stored answers (`browser/survey_results.py:98-108`); `converters/markdown.py:33-40` inserts values without escaping; `converters/html.py:8,14-16` converts Markdown with markdown2 without sanitizing; and `browser/survey_result_detail.pt:82-83` inserts the result as structure. The detail page is permission-protected (`browser/configure.zcml:92-96`), so an attacker can submit the value publicly and target an Editor or Manager reviewing results. The victim must click the link; the resulting script runs in the Plone page’s origin. No in-repository `script-src` policy was found.

Remediation: treat answers as text by default, or sanitize rendered HTML using a strict allowlist of tags, attributes, and URL schemes. Do not rely on regex-only HTML filtering.

### Medium — spreadsheet formula injection in CSV and XLSX exports

The submission validator accepts formula-leading strings such as `=1+1`. `converters/csv_export.py:10-16` writes values unchanged; `converters/xlsx_export.py:11-20` appends values directly to cells. Local verification confirmed the CSV round-trip preserves the formula and openpyxl writes the XLSX cell as a formula.

A public respondent can plant formulas that execute or create risky links when a survey Editor or Manager opens an export. This is not a claim of guaranteed code execution; impact depends on the spreadsheet client and formula.

Remediation: escape formula-leading values consistently in every spreadsheet export, including values beginning with `=`, `+`, `-`, or `@`.

### Medium — no enforced rate limit on public submissions

`save_poll` does not call `check_rate_limit`. The helper in `monitoring.py:647-699` is used for dashboard status (`browser/survey_monitor.py:84-87`), not admission control, and returns “allowed” when its cache is unavailable or errors. Public submissions remain bounded per request, but not by rate or total volume. Repeated submissions can grow storage and trigger configured downstream actions. The SQL result list loads all matching rows (`storage.py:300-314`), which amplifies the impact as a survey grows.

Remediation: enforce per-IP/per-survey quotas or a distributed rate limiter at the edge or application layer. Keep security decisions fail-closed when the limit store is unavailable.

### Medium, local-write prerequisite — DiskCache unsafe deserialization advisory

The Plone runtime uses `diskcache` 5.6.3. `pip-audit` reported PYSEC-2026-2447, which affects DiskCache through 5.6.3: a party able to write to the cache directory can achieve code execution when the application reads the cache. This is not a demonstrated remote exploit through the submission API; it requires cache-directory write access. OSV listed no fixed release at review time.

The code already supports an SQL KV backend; prefer the shared PostgreSQL/MySQL backend for production replay and one-time-use state, or strictly isolate and permission the cache directory. Advisory: https://osv.dev/vulnerability/PYSEC-2026-2447

### Low, build-context dependent — setuptools source-distribution advisory

The repository’s build environment pins setuptools 81.0.0 (`requirements.txt:4-6`), flagged as PYSEC-2026-3447; the advisory’s fix is 83.0.0. It affects source-distribution exclusions when Unicode-normalized filenames and exclusion patterns differ on macOS APFS/HFS+. The current `MANIFEST.in` rules are ASCII (`MANIFEST.in:1-11`) and the source-distribution workflow runs on Ubuntu and installs the latest setuptools (`.github/workflows/sdist.yml:35-61`), so I found no applicable current CI path. Raise the development/build pin to the fixed release and retain the current exclusion checks. Advisory: https://osv.dev/vulnerability/PYSEC-2026-3447

An initial local environment scan also reported pip 26.1.2, associated with PYSEC-2026-3721. The current `requirements.txt` pins pip 26.2, and the `.venv` later reported 26.2; treat the earlier result as environment drift and verify the exact release image’s build tooling.

## Residual and hardening risks

- SSRF protections are materially better than an unrestricted-URL design: `ssrf.py:35-90` resolves the hostname and blocks private/reserved addresses, and `subscribers.py:584-589` disables redirects. A DNS time-of-check/time-of-use gap remains because the request performs a fresh resolution after validation. Exploitation requires an editor-controlled endpoint and adversarial DNS. Pin the validated address or enforce network egress restrictions.
- `test_plone60.cfg:4` follows a mutable upstream `master` buildout configuration and is part of the Docker build chain. Pin it to an immutable revision. The Docker image also runs as root (`Dockerfile:50` has no non-root user); run the application with least privilege.
- The in-repository CSP match sets `frame-ancestors *` in a view (`browser/views.py:1264-1266`); it does not supply a `script-src` mitigation for the XSS finding.

## Positive controls verified

- Mutating POSTs use Plone’s `CheckAuthenticator` (`browser/views.py:190-193,561-566`).
- Embedded JWTs are signed, time-limited, origin-bound, and one-use tracked; the configuration route checks the survey subject.
- Submission payload size, file count, file MIME/signature, filename, and selected unsafe markup are validated. Server-side SurveyJS validation is enabled by default for surveys (`content/survey.py:274-280`).
- Results pages and detail views require `ModifyPortalContent` (`browser/configure.zcml:57-60,92-96`).
- The SQL KV backend supports shared atomic state; it is an available mitigation for host-local DiskCache state.

## Verification and limitations

- `make test`: Plone suite ran 882 tests with zero failures/errors and 69 skipped; pytest subset passed 113 tests. Some AI tests emitted non-fatal warnings about worker threads left behind.
- Targeted local probes reproduced the accepted active anchor, its preservation in rendered submission HTML, and formula handling in CSV/XLSX.
- `pip-audit` was run against the local environment and the runtime DiskCache egg; this was not a complete inventory of the final Docker image.
- No live public instance, production secret configuration, or external reverse-proxy controls were tested. Independent delegated reviews could not complete because the provider returned HTTP 401.
