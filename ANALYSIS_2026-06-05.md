# 360-Degree Code Analysis — `zopyx.surveyjs`

**Date:** 2026-06-05  
**Codebase:** ~20,582 lines of Python across 96+ source files; ~115 static frontend assets; 5 ZCML configurations; 13 Page Template files; 17 test modules.

---

## 1. Architecture

### 1.1 Strengths

1. **Well-designed event-driven submission pipeline** — `ISurveyJSFormSubmittedEvent` with independent subscribers (store, email, notification, POST, monitoring, debug log). Each subscriber has a single responsibility; failures in one do not affect others.

2. **Dual storage abstraction with clean interface** — `ResultStorage` ABC with `ZODBResultStorage` and `SQLResultStorage` implementations, plus parallel `ITokenStore` for tokens. Factory functions decouple consumers from concrete implementations.

3. **Modular converter system** — 9 export formats (text, markdown, HTML, PDF, CSV, Excel, XML, Word, JSON) encapsulated in individual modules with shared helpers in `common.py` and `types.py`. Each writer follows a consistent function signature.

4. **Defense-in-depth security architecture** — Three token types (authenticity tokens for CSRF/replay, trusted access for viewer auth, embed tokens for cross-origin security). Each has its own TTL, replay protection via diskcache, and audit logging.

5. **Comprehensive auditing infrastructure** — Persistent (ZODB-based via `zopyx.plone.persistentlogger`) and standard `logging`-based audit trails with smart redaction of sensitive fields and compact summaries for large payloads.

6. **Appropriate use of Plone conventions** — Dexterity content types with XML FTIs, ZCML-based registration, GenericSetup profiles, z3c.jbot for template overrides, and `browser:resourceDirectory` for static assets.

7. **Feature toggle system** — `features_enabled` registry setting controls AI, chatbot, dashboard, PDF generator, and fillable PDF features independently.

### 1.2 Weaknesses

1. **Massive God Object in `views.py`** — The `Views` class (1161 lines) mixes 30+ responsibilities: form rendering, JSON serialization, poll saving, result management, export downloads, date filtering, auth token generation, trusted access validation, embedding logic, metadata display, and license key management.

2. **Implementation duplication** — Export format dispatch logic duplicated nearly verbatim in `subscribers.py:_write_export` (45 lines of if/elif) and `browser/services/export.py:write_export` (40 lines of if/elif). `CONVERTER_FORMATS` metadata duplicated between `views.py` and `subscribers.py`.

3. **Leftover debug code** — `breakpoint()` at `views.py:742` halts the Python interpreter in production deployments.

4. **Overly broad Python version constraint** — `python_requires=">=3.12,<3.14"` excludes Python 3.11 (still common in Plone 6.0 LTS) and guards against Python 3.14 for a speculative Rust dependency issue.

5. **Heavy mandatory dependencies** — `weasyprint` (requires system GTK/Pango/Cairo), the entire `llm` ecosystem (five LLM provider packages), and `sqlmodel` are declared as `install_requires` rather than optional extras. Only `test` exists in `extras_require`.

6. **JavaScript dependency management by vendoring** — 30+ minified SurveyJS files, tabulator, marked, and tanstack-table committed directly to `browser/static/`. No `package.json`, no npm/yarn lock, no build pipeline.

7. **Fragmented caching infrastructure** — Three separate `diskcache.Cache` instances in `auth.py`, `embed_security.py`, and `monitoring.py` with different path resolution, expiry policies, and no shared configuration.

8. **Weak uninstall profile** — `profiles/uninstall/` only removes the browser layer. Does not clean up content types, permissions, registry entries, catalog indexes, or annotation data.

9. **Inconsistent error handling patterns** — Mix of custom exceptions (`AuthTokenError`, `EmbedSecurityError`), `json_error()` helper, and bare `except Exception: logger.exception(...)`. No clear transaction boundary management across ZODB + SQL + external HTTP.

10. **String-based coupling** — Survey actions (`"store"`, `"mail"`, `"mail-notification"`, `"post"`), access modes (`"public"`, `"trusted"`, `"trusted-tokens"`), storage backends (`"zodb"`, `"rdbms"`), embedding modes (`"none"`, `"iframe"`, `"direct"`), and annotation keys are string literals scattered across dozens of files with no centralized enumeration.

### 1.3 Top 5 Recommendations

| # | Issue | Impact | Fix | Priority |
|---|-------|--------|-----|----------|
| 1 | Decompose the God Object `Views` class | Untestable, fragile, hard to modify | Extract `FormSubmissionService`, `ResultExportService`, `MetadataService`; keep `Views` as thin orchestration | **HIGH** |
| 2 | Consolidate export format dispatch | Changes needed in 3+ places per new format | Create `FORMAT_REGISTRY` dict in `converters/__init__.py`; derive `CONVERTER_FORMATS` from it | **HIGH** |
| 3 | Separate heavy deps into `extras_require` | Forces AI/PDF deps on all installs | Use `extras_require` groups: `pdf`, `ai`, `sql`, `all`; add graceful import guards | **HIGH** |
| 4 | Unify fragmented caching infrastructure | Resource leaks, inconsistent behavior | Create `cache.py` with central `get_cache(namespace)` factory; namespace-prefixed subdirectories | MEDIUM |
| 5 | Add formal service layer between views and storage | Views untestable without Plone fixtures | Create `FormSubmissionService` and `ResultQueryService`; provide as Zope utilities | MEDIUM |

## 2. Security

### 2.1 Strengths

1. **Multi-layered token authentication system** — Three distinct token types (authenticity, trusted access, embed) with HMAC signing, time-bound validity, origin binding, replay protection via diskcache, and fail-closed patterns on cache unavailability.

2. **Comprehensive audit logging with privacy-aware redaction** — Automatic redaction of sensitive fields (email addresses, secrets, API keys, endpoint URLs). Form JSON summarized as SHA-256 hash + metadata rather than raw content.

3. **Defense-in-depth embed security** — HTTPS enforcement for non-localhost origins, origin-to-allowlist validation, JWT-based embed tokens with HMAC signatures, one-time-use enforcement, CORS headers restricted to allowlisted origins.

4. **Parameterized SQL queries via ORM** — All database operations use SQLModel/SQLAlchemy ORM patterns (`session.get()`, `select().where()`). Raw SQL in `get_stats()` uses named parameters (`:site_id`, `:survey_id`).

5. **Proper Plone permission integration** — Custom permissions with role mapping, `CheckAuthenticator` for CSRF on form POST operations, appropriate use of `cmf.ModifyPortalContent` and `cmf.ManagePortal`.

6. **Payload size limits** — `max_payload_size_mb` (default 1MB) enforced with both Content-Length header check and post-parse size validation in `save_poll()`.

7. **AI API key stored as `schema.Password`** — Uses Plone's password field type which masks the value in the admin UI.

### 2.2 Weaknesses

1. **Hardcoded credentials in environment files** — `.env` contains live OpenAI API key, SMTP password, and SMTP username. `surveyjs.licensekey` is committed to the repository.

2. **`breakpoint()` debugger in production code** — Line 742 of `views.py` contains a bare `breakpoint()` call that halts Python execution on every form submission.

3. **Sensitive data logged to stdout** — `log_survey_submission()` subscriber prints complete form submission data (including all PII) to stdout via `print()`. Full authentication tokens logged verbatim in `auth.py:365`.

4. **No encryption at rest for survey responses** — All submissions stored as plain JSON in ZODB annotations or SQL `entry_json` TEXT column. No field-level or record-level encryption.

5. **API keys exposed via `os.environ`** — In `ai.py:533-534`, `engine.py:83-85`, and `engine.py:64`, API keys are injected into `os.environ`, making them readable by subprocesses, error tracebacks, and process inspection.

6. **`save-poll` endpoint has `zope2.View` permission** — Accessible to unauthenticated users. In `public` mode, there is no server-side check beyond `_require_trusted_access()` and `_require_auth_token()`, both of which can be disabled.

7. **SSRF risk via HTTP POST action** — `post_submission_payload()` makes outbound HTTP requests to user-configured URLs with no validation beyond `schema.URI`.

8. **No file upload size limit** — Neither AI document upload (`ai.py`) nor fillable PDF upload (`fillable_pdf.py`) enforce a maximum file size.

### 2.3 Top 5 Recommendations

| # | Issue | Severity | Exploit Scenario | Fix | Priority |
|---|-------|----------|------------------|-----|----------|
| 1 | Live credentials in `.env` + committed license key | **CRITICAL** | Attacker with filesystem access extracts OpenAI key; committed license key in git history forever | Rotate credentials; remove from `.env`; add `*.licensekey` to `.gitignore`; use secrets manager | Immediate |
| 2 | `breakpoint()` in production code | **HIGH** | Every submission triggers pdb, halting processing; thread pool exhaustion | Remove line 742; add pre-commit hook for `debug-statements` | Immediate |
| 3 | Survey data stored unencrypted (PII at rest) | **HIGH** | ZODB breach or backup theft exposes all historical PII | AES-256-GCM encryption; add `sensitive_fields` config on survey content type | High |
| 4 | API keys in `os.environ` + sensitive data logged | **HIGH** | Process inspection (`/proc/<pid>/environ`) exposes keys; error tracebacks leak them | Pass keys directly to clients; use context manager for temp env vars; redact tokens in logs | High |
| 5 | Missing CSRF on save-poll; no input sanitization | MEDIUM | Cross-site form submission via hidden form on attacker site; stored XSS in results view | Add `CheckAuthenticator`; sanitize with `bleach`/`nh3`; wire rate limiter | Medium |

| # | Finding | Severity | Location |

## 3. UX (User Experience)

### 3.1 Strengths

1. **Exceptional error state design** — Five distinct error states (missing token, invalid/expired token, revoked token, service unavailable, generic) with tailored icons, actionable recovery steps, and semantic color coding. The strongest UX pattern in the codebase.

2. **Comprehensive unsaved changes protection** — Editor tracks dirty state with pulsing red banner, inline indicator on save button, and `beforeunload` handler to prevent accidental navigation.

3. **Centralized asset management** — `survey_assets.pt` macro system provides single source of truth for all SurveyJS resource loading, making updates and theme swaps straightforward.

4. **Fullscreen mode pattern** — Consistently implemented across viewer, editor, results, and template viewer with keyboard escape support, URL parameter persistence, and `aria-pressed` state management.

5. **Rich results management table** — Custom vanilla JS table (1353 lines) with sorting, column filtering, search, pagination, column resizing (localStorage persistence), batch operations with type-to-confirm safety, and modal-based detail views.

6. **Privacy-aware design** — Token-based access with one-time-use enforcement, embed security with origin validation, and cookie notice on login.

7. **i18n coverage** — All template strings use `i18n:translate`; client-side translation function available; survey translation editing integrated into editor.

8. **Helpful chatbot** — Pre-defined quick prompts for common configuration questions.

### 3.2 Weaknesses

1. **`alert()` for user-facing errors** — Used in `viewer.js` (line 488), `results.js` (lines 371, 393, 1144, 1187, 1256), and `ai.js` (line 72). Blocks the main thread, is not stylable, and may not be announced properly by screen readers.

2. **No loading indicator during form JSON fetch** — Viewer hides the entire survey container until load completes, showing users a blank area with no feedback.

3. **Debug artifact in production code** — `breakpoint()` on `views.py:742` halts execution in any Python debugging environment.

4. **Blocking script loading** — All SurveyJS libraries (3MB+ combined) load synchronously without `async`/`defer`, blocking page rendering. External CDN dependencies (Google Fonts, Quill, unpkg) add fragility.

5. **No focus management in modals** — Results page has 5 modal dialogs with no focus trapping and no focus return on close, violating WCAG 2.4.3 (Focus Order).

6. **Inconsistent visual systems** — Mixes `survey-action-button` pill styles with Plone `btn btn-primary` classes, inline styles in `survey_versions.pt`, and unique `tv-*` naming in token store.

7. **Missing mobile-first design for navigation** — Action bar with up to 10 buttons has no mobile-adaptive layout; buttons overflow or wrap ungracefully on small screens.

8. **No cache-busting on static resources** — Resource URLs lack version hashes, potentially causing stale-cache issues after updates.

9. **External font dependency (privacy concern)** — `survey-core.min.css` loads Google Fonts, sending user IP addresses to Google and potentially violating GDPR.

10. **No RTL (right-to-left) CSS support** — Despite supporting Arabic and Hebrew language options, there is no RTL layout handling in custom CSS.

### 3.3 Top 5 Recommendations

| # | Issue | User Impact | Fix | WCAG | Priority |
|---|-------|-------------|-----|------|----------|
| 1 | Remove `breakpoint()` from `views.py:742` | Breaks all form submissions in debug environments | Delete the `breakpoint()` statement | N/A | **HIGH** |
| 2 | Replace `alert()` with inline error notifications | Blocking, inaccessible error UX with no recovery path | Implement shared toast/notification system; show inline errors near submit button with retry | 4.1.3 (Status Messages) | **HIGH** |
| 3 | Add loading indicator during form JSON fetch | Blank page on slow connections; users think page is broken | Add spinner/skeleton in `#surveyViewerContainer` before fetch, hidden on success/error; reuse `.surveyjs-spinner` CSS | N/A | **HIGH** |
| 4 | Implement focus trapping in modal dialogs | Keyboard-only users lose place; interact with hidden elements behind modal | On open, save focused element; trap Tab/Shift+Tab; restore focus on close; add `aria-modal="true"` | 2.4.3 (Focus Order) | **HIGH** |
| 5 | Defer scripts + use fontless CSS + add cache busting | Slow first paint; Google Fonts privacy leak; stale caches | Add `defer` to `<script>` tags; use `survey-core.fontless.min.css`; add `?v=` query params to resource URLs | 2.2.1 (Timing Adjustable) | MEDIUM |
